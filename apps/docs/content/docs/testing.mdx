## Automated

| Area | What the tests check |
|---|---|
| Instruction allowlist | Every valid move passes; attack variants are refused (wrong amount, wrong destination, approvals, authority changes, extra transfers, Token-2022, unknown programs, second signers, redirected or fee-carrying Jupiter routes, over-wrapping, missing lookup tables). Blocks every build. |
| Quote checks | Our signature check equals NEAR Intents' SDK on real mainnet quotes; any change to a signed field fails; unsigned fields are checked separately; expired, misaddressed and over-charging quotes are refused. |
| Live (read-only) | Fresh dry quotes verify; the fee split matches what we disclose; every kind of move is simulated against mainnet from real wallets that hold the right balances, and the deposit address receives exactly the quoted amount. Nothing is signed or sent. |
| Zcash | Unified address decoding against ZIP 316 test vectors; key derivation; a private local Zcash test network (regtest) where a payment to a derived address is found by our scanner and the wallet restored in zcash-devtool (the Zcash developers' command-line wallet) sees it. |
| App | Every screen and state in a browser on phone and desktop sizes, with network-level mocks: wallet creation and backup check, exit, top-up, buys, refunds, cancellations, pauses, regions, expiry, slow moves, accessibility. Each transaction the app hands to the wallet is re-checked against the allowlist from outside the page. |
| Server | Region rules, incident detection on NEAR Intents' real status data, counter verification and storage, sanctions list parsing. |

Run them: `pnpm test`, `pnpm test:live`, `pnpm --filter @zecdoor/app e2e`.

## Mainnet transactions

Every mainnet transaction we make while testing is listed here with its Solana signature, Zcash transaction and NEAR
Intents status. They run through the app's own code, driven in a browser on mainnet with a test wallet
([`scripts/mainnet/app-run.ts`](https://github.com/ZecDoor/zecdoor/blob/main/scripts/mainnet/app-run.ts)); before
signing, each transaction is re-checked against the allowlist from outside the page. The phone runs below were signed by
hand in the Phantom app. Moves and buys opened to everyone on 12 October 2026, after these runs passed.

The USDC for the buy came from swaps inside the test wallet in Phantom, outside ZecDoor. Each record was rebuilt from the
chain with [`scripts/mainnet/inspect-landed.ts`](https://github.com/ZecDoor/zecdoor/blob/main/scripts/mainnet/inspect-landed.ts):
NEAR Intents' signature on each quote is valid, and every instruction we built landed unchanged.

What the phone runs found:

- **Phantom adds two instructions.** On every run Phantom added two Lighthouse assertions (`AssertAccountInfoMulti` and
  `AssertTokenAccountMulti`), wallet guards that cost 83 bytes. It changed nothing we built. Our allowlist runs before
  Phantom sees the transaction, so it checks only what ZecDoor built; the largest move, a top-up, still fits with 181
  bytes to spare.
- **A reload lost the chosen destination.** Before these runs, on the same phone, choosing "Use my Zcash wallet" and
  pasting an address did not stick: "Lands in" went back to "New shielded wallet". Temporary diagnostics on the preview
  showed why: Phantom's in-app browser reloaded the whole page when the app moved to its home screen with a `#/` link,
  which cleared everything held in memory. The app now moves between screens with `history.pushState`, never a page-level
  link, and a test reproduces the reload (`3cbfffa`). Nothing was signed while the bug was there.
- **A fee row counted the swap.** The review's "Solana fees and deposit" row included the SOL being swapped in a top-up
  (about 0.0154 SOL instead of about 0.0030). Fixed before the runs (`8a5a869`), with a test.
- **More arrives than `amountOut` says,** as in B1: each note held 7,000 zat more, because the bridge charged 25,000 zat
  for the Zcash payout, not the 32,000 its quote shows.

### B1: top up and shield, one transaction (5 Oct 2026)

A wallet holding 0.0003 ZEC, below the bridge minimum, moved all of it into a new wallet made in the app, topped up by a
Jupiter swap from SOL inside the same transaction. **Passed:** NEAR Intents credited the combined transaction, and the
ZEC arrived in the shielded pool 2 minutes 13 seconds after signing. The transaction was signed by our test key, standing
in for Phantom. **[Check it again, live in your browser](https://zecdoor.0xo.in/app/#/proof)**: the page verifies NEAR
Intents' signature on the quote, reads the Solana transaction from a public RPC and finds the Zcash transaction's block on
lightwalletd.

Two findings:

- **Transaction ID byte order.** NEAR Intents' status reports the Zcash transaction ID in the same byte order as our
  scanner and as block explorers: the Zcash Block Explorer (mainnet.zcashexplorer.app) finds `2fac74…06d6` in block
  3,507,539 and nothing for the reversed bytes (checked 7 Oct 2026; first checked on Blockchair, 6 Oct).
  The app matches arrival by address and amount, so this needs no change.
- **More arrives than `amountOut` says.** The note held 7,000 zat (0.00007 ZEC) more than the status's `amountOut`: the
  bridge charged 25,000 zat for the Zcash payout, not the 32,000 its quote shows. The quote's minimum is what we promise.

### Refund probe (5 Oct 2026)

To see where NEAR Intents reports a refund, we sent a deposit smaller than its quote asked for (test tooling, outside the
app; the app's transaction always sends the exact amount). **Refunded** to the sending wallet 31 minutes later, at the
quote's deadline.

| Step | Record |
|---|---|
| Starting balance (bought for the test) | 0.0003 ZEC, Solana [`3mxUQB…hzhmf`](https://explorer.solana.com/tx/3mxUQB7epoY265fW1QfXyLkde5XkUTiVFyYxffksFPBq5FdPE2LPESydp3DoZuLd44w37wR8Fi1ZDs7uNS6hzhmf) |
| Deposit of 0.0003 ZEC against a quote for 0.00136669 | Solana [`5BPG29…MSXTuhM`](https://explorer.solana.com/tx/5BPG29y5mu52DigA2uGCLtXHG17a26njTx3vYhp52sFGHRWwKzKHpfG9y4drqWR6paVGGV5vxc8FJjjdmMSXTuhM), deposit `7hQaoUcuy1SWJj7s3TfFJ8vwPwmTmgUGK27VabuBY7JH` |
| NEAR Intents | PENDING_DEPOSIT → INCOMPLETE_DEPOSIT (1 minute) → **REFUNDED** (31 minutes), `refundReason` PARTIAL_DEPOSIT |
| Refund | Solana [`3kdVEQ…dt8mSXcP`](https://explorer.solana.com/tx/3kdVEQS27gJTnHXzFvRrNWJaWdAH2aCZg9qr3CdKFLSxXM5yT8Mt1uQoh4wXhiCN6ux5djwjrJLjbRFadt8mSXcP): 0.0002924 ZEC back to the sending wallet (`refundFee` 763 zat) |

**Finding: where the refund is reported.** NEAR Intents lists the refund transaction as a second entry in
`originChainTxHashes`, after the deposit, and leaves `destinationChainTxHashes` empty. The app already takes the Solana
signature that is not the user's own deposit; a test now runs it against this real status.
